# Seven-day launch plan

No public post or unsolicited contact occurs without maintainer confirmation.

## Day 1 — controlled Show HN launch

- Final read-through of the live README and demo from a logged-out browser.
- Upload `docs/assets/social-preview.png` through the confirmed personal GitHub account.
- After explicit approval, publish the prepared Show HN post once.
- Remain available for the first two hours and answer technical questions with links to evidence,
  threat model, or code.
- Record baseline metrics before and 24 hours after; do not ask for votes.

## Day 2 — convert feedback into repository clarity

- Group questions into onboarding, trust model, portability, and integrations.
- Fix only obvious documentation friction or reproducible defects.
- After explicit approval, publish the Welcome Discussion and route detailed feedback there.
- Do not open roadmap issues merely to make the repository look active.

## Day 3 — technical depth

- Incorporate valid HN criticism into the article draft.
- After explicit approval, publish “Why AI-generated code needs independent verification” on either
  Dev.to or Hashnode, not both simultaneously.
- Use the exact demo visual and canonical repository link.

## Day 4 — one proof-of-integration

- Select one Priority A target based on observed questions, likely Cline, OpenHands, Goose, E2B, or
  Dagger.
- Build the integration in a local fork/example without contacting maintainers.
- Measure setup time and capture a real passport.
- If the integration is weak or duplicative, document the result internally and do not pitch it.

## Day 5 — DevOps community test

- Check current r/devops rules and recent duplicate topics.
- After explicit approval, post the CI `continue-on-error` case study, not the Show HN text.
- Ask how teams protect workflows and policy files; do not ask for stars.
- Answer every substantive reply and correct mistaken claims.

## Day 6 — focused maintainer/community outreach

- Choose at most two projects where Day 4 produced concrete value.
- Use only an existing relevant Discussion, integration channel, or community forum.
- Disclose PatchWitness maintainer affiliation and share the runnable integration result.
- Send no cold direct messages and no follow-up if unanswered.

## Day 7 — evidence-based review

- Record the weekly scorecard from `GROWTH_METRICS.md`.
- Separate discovery signals (views/stars) from adoption signals (runs/downloads/issues/integrations).
- List the top three real friction points.
- Decide whether the next week should focus on documentation, one adapter, a bug fix, or no change.
- Keep `NOT READY TO APPLY` for Codex for Open Source unless broad adoption and ecosystem importance
  are demonstrated by real data.

## Stop conditions

Pause promotional posting if:

- the demo or install path fails for a new user;
- a security report suggests unsafe default behavior;
- community feedback identifies a misleading claim;
- posts are being removed under community self-promotion rules; or
- there is no capacity to respond constructively to users.
