# Why AI-generated code needs independent verification

> Publication draft for Dev.to or Hashnode. Suggested canonical URL after publication:
> `https://github.com/pangxueyuan2-creator/patchwitness`

Coding agents have changed the economics of software modification. A task that once occupied an
engineer for an afternoon can now produce a plausible patch in minutes. That is a real advance. It
also moves the bottleneck.

The scarce resource is no longer always the first implementation. It is the reviewer's ability to
establish what changed, whether the change stayed inside its intended boundary, whether the claimed
checks actually ran, and whether the patch altered the machinery used to verify itself.

This is not an argument against coding agents. It is an argument for separating code production from
the evidence used to trust the result.

## A completion summary is a claim

A capable coding agent usually ends a task with a summary:

- which files it changed;
- what behavior it implemented;
- which tests it ran;
- whether those tests passed; and
- what a reviewer should examine.

That summary is helpful. It is still generated by the same system that selected and made the
changes. If the agent missed a file, misunderstood the requested scope, ran the wrong command, or
modified CI, the summary is not an independent record of those facts.

The same distinction already exists elsewhere in engineering. A build log is not replaced by a
developer saying “the build passed.” A signed artifact is not replaced by a message saying “this is
the artifact I built.” Useful claims become more trustworthy when another mechanism can reproduce or
verify them.

For coding-agent changes, that mechanism should be boring, deterministic, and easy to inspect.

## “Tests passed” is narrower than it sounds

Imagine a patch with three edits:

1. `src/pricing.py` gains a correct `discount()` function;
2. `tests/test_pricing.py` gains a passing test; and
3. `.github/workflows/ci.yml` gains `continue-on-error: true`.

The agent runs the unit tests. They pass. The statement “tests passed” is true.

But the patch also weakened the control plane that determines whether future failures block a merge.
Test execution answers one question: did this command exit successfully? It does not automatically
answer another: did the patch preserve the verifier around that command?

Branch protection and CODEOWNERS can help, but many repositories have incomplete coverage, and local
agent workflows often happen before a pull request exists. The useful primitive is an explicit task
contract evaluated against policy the patch cannot rewrite.

## A real, reproducible example

PatchWitness is an open-source experiment in that primitive. Its repository contains the exact
scenario above as an executable demo. It creates a disposable Git repository, commits a trusted
base, applies the mixed agent patch, runs two real unit tests, invokes PatchWitness, and verifies the
resulting Change Passport.

Run it with Git and Python 3.11 or newer:

```bash
git clone https://github.com/pangxueyuan2-creator/patchwitness.git
cd patchwitness
python demo/run_demo.py
```

The repository tests report:

```text
Ran 2 tests in 0.000s

OK
```

PatchWitness then reports:

```text
PatchWitness FAIL
  3 files | 10 lines | 1/1 checks
  Risk: LOW (15/100) | 1 direct dependents
  ERROR PW002 [.github/workflows/ci.yml]: path is outside the approved scope
  ERROR PW003 [.github/workflows/ci.yml]: protected verification or control-plane file changed
```

The test check passed. The gate failed for a different, independently evaluated reason.

The committed transcript and JSON evidence are generated by the demo rather than typed into the
README. Machine-specific filesystem paths are normalized; the status, counts, findings, and evidence
hash come from the real run.

## What goes into a Change Passport?

The phrase “Change Passport” describes a portable evidence record for one repository change. In
PatchWitness schema v1, that includes:

- the resolved base and head revisions;
- changed paths, status, line counts, and binary status;
- before and after SHA-256 values for each file;
- the contract and where it was loaded from;
- every check command, exit code, duration, timeout state, redacted excerpt, and output hash;
- stable policy findings such as `PW002` and `PW003`;
- a conservative dependency impact graph for Python, JavaScript, and TypeScript;
- environment facts and extension output; and
- a canonical payload SHA-256 for offline integrity verification.

The JSON is designed for machines, not only people. The same evidence can be rendered as Markdown,
SARIF, GitHub workflow annotations, or consumed through the Python SDK and MCP tools.

## The trusted base matters

A policy file inside the working tree is convenient, but it creates a circular trust problem. If a
pull request can change `.patchwitness.toml` and immediately evaluate itself against the new file, it
can delete the rule that would have blocked it.

PatchWitness supports base-authoritative policy:

```bash
patchwitness gate \
  --base "$BASE_SHA" \
  --policy-ref "$BASE_SHA" \
  --clean-room \
  --output change-passport.json
```

`--policy-ref` loads the contract from the resolved Git commit rather than from the patch under
review. The evidence records that source. A change to the working-tree contract is itself visible,
but it cannot silently weaken the rules used for the current decision.

This does not eliminate the need to protect the base branch. It makes that trust assumption explicit
and inspectable.

## Why not use another LLM reviewer?

Semantic review by a model can be useful. It can identify suspicious logic, explain unfamiliar code,
suggest missing tests, and prioritize human attention. PatchWitness is not a replacement for that.

The distinction is the trust root. Questions such as “which Git paths changed?”, “what exit code did
the test process return?”, and “did this patch touch a protected workflow?” do not require a
probabilistic judge. They can be answered directly and deterministically.

A strong workflow can use both layers:

1. deterministic evidence for scope, execution, integrity, and known policy;
2. static and dynamic security tools such as CodeQL, Semgrep, or Trivy;
3. optional AI review for semantic hypotheses; and
4. a human decision for consequential changes.

The Change Passport can record the exit status and output hash of those repository-owned tools
without pretending to subsume them.

## Local-first does not mean sandboxed

PatchWitness core has zero runtime dependencies and does not upload source. Its clean-room mode
creates a disposable Git worktree from the base revision, disables repository hooks during
materialization, applies the patch, and runs configured checks there.

That is useful isolation from a dirty developer checkout. It is not a security boundary equivalent
to a container, virtual machine, or kernel sandbox. Repository checks are commands, and commands can
be dangerous. High-assurance deployments should run PatchWitness inside an appropriate sandbox with
restricted credentials, network, and filesystem access.

Precise limitations matter more than ambitious labels.

## Trying it on an existing repository

Install the current release from GitHub:

```bash
pipx install "https://github.com/pangxueyuan2-creator/patchwitness/releases/download/v0.2.0/patchwitness-0.2.0-py3-none-any.whl"
```

Initialize a contract:

```bash
cd your-repository
patchwitness init
```

Replace the starter test command with the real command for the repository, commit the contract to
the base branch, and run:

```bash
patchwitness gate --base origin/main --policy-ref origin/main --clean-room
```

For a narrow agent task, create a task contract with explicit allowed paths and checks:

```bash
patchwitness contract new GH-123 \
  --goal "Fix token refresh without changing the public API" \
  --allow "src/auth/**" \
  --allow "tests/auth/**" \
  --check "tests=python -m pytest tests/auth"
```

The most useful early adoption pattern is observation before enforcement: capture passports on a few
real pull requests, inspect noise and missing evidence, then make the gate required only after the
contract reflects the repository.

For CI, PatchWitness Gate is also available on the
[GitHub Marketplace](https://github.com/marketplace/actions/patchwitness-gate).

## What independent verification does not prove

A passing Change Passport does not prove that:

- the implementation matches the user's intent;
- the tests are complete;
- the dependency graph understands every dynamic import;
- the evidence producer has a particular identity;
- the execution environment was uncompromised; or
- the change is safe to deploy.

It proves narrower claims recorded in the evidence. That narrower scope is a strength when it is
stated clearly.

## The next interface between agents and engineering systems

Coding agents will keep improving. OpenAI, ChatGPT, Codex, and the wider agent ecosystem have already
made AI-assisted engineering practical for a broad developer audience. Better agents do not make
independent verification obsolete; they make a reliable interface between autonomous work and
engineering control systems more valuable.

That interface should be portable enough for local tools, CI, code hosts, orchestration systems, and
future attestation formats. It should also be open to criticism and extension.

PatchWitness is an Apache-2.0 public alpha, not a production-proven standard. The project is looking
for feedback on the evidence schema, trust model, language adapters, and CI integration surface—not
manufactured adoption metrics.
